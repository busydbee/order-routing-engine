## Order Routing Engine — Design 

**Created:** 2026-08-12
**Last updated:** 2026-08-13

This documents how the routing engine decides, what it optimizes for, the approaches considered and rejected, the assumptions/shortcuts taken, and what would need to be built before this went near a real merchant.

---

## 1. Primary objective

**Protect the promised delivery date (EDD).** The shift to a promise-date model makes the network "strictly responsible" for the date shown to the shopper at checkout — not just for shipping cheaply. Cost is optimized *underneath* that constraint and every cost tradeoff made to hit (or miss) a date is logged, not hidden.

---

## 2. Approaches considered

Four routing methodologies were evaluated. **Pure Greedy (FIFO)** was ruled out early — processing orders in strict arrival order lets an order due in two weeks steal the optimal inventory from an order due tomorrow simply because it arrived first, which directly attacks the primary objective. In design discussion it is the conceptual floor; in this repo the **naive** baseline (Section 3) implements that floor for `report.md`.

The three real contenders:

| Approach | Core logic | Exact trade-off |
| --- | --- | --- |
| **Urgency-Sorted** | Sort the batch by promised date (ascending); route tightest deadlines first, claiming inventory as you go. | **Gains:** protects the promise directly; trivially explainable ("Order A was routed before Order B because it had an earlier promise date"). **Costs:** geographic/cost blindness *within* the same date — two orders due the same day are treated as equally urgent even if one is far more flexible than the other, so cost-saving swaps between same-day orders are left on the table. |
| **Regret Cost** | For every order, calculate the cost delta between its cheapest and second-cheapest feasible option; route the highest-delta ("least flexible") orders first. | **Gains:** approximates a batch-level optimum cheaply — inflexible orders get first claim on scarce/cheap inventory, and flexible orders absorb the leftover cost, which is exactly what a joint optimizer would arrive at. Still a single sorted pass, so still explainable ("Order X was routed first because its backup option was $20 more expensive than its best option"). **Costs:** has to compute and cost every feasible option for every order before it can sort anything, so it needs a fast, reliable rate/transit lookup for the whole batch up front; on its own it treats cost-delta as the sort key, not the promise date, so it needs the date folded in explicitly or it can silently deprioritize an urgent-but-flexible order. |
| **ILP (global solver)** | Model the whole batch as one mathematical program and solve for the true global-minimum-cost assignment across all orders and constraints simultaneously. | **Gains:** the only approach that can see and exploit true cross-order swaps (e.g., re-assign a flexible order to free up scarce inventory for an inflexible one) — the residual value a sorted pass can't reach. **Costs:** decisions are a solver output, not a chain of comparisons — operations cannot reverse-engineer *why* a specific order landed where it did, which directly violates "the decision should be explainable, not a black box." It's also computationally too slow for real-time, per-order decisioning at production volume. |

**This mirrors how production fulfillment systems route orders today.** Distributed Order Management (DOM) platforms — Kibo, IBM Sterling, Manhattan, Fluent Commerce — run a configurable, rule-based routing engine as the live per-order decision-maker: cost, speed, proximity, and inventory rules evaluated per order, in real time. Mixed-integer/ILP solvers show up in these networks too, but as periodic network-design or safety-stock planning runs (minutes of solve time is fine), or as an offline benchmark against the live heuristic — never as the thing deciding an individual order in the request path, because MIP solve time is incompatible with sub-second, per-order decisioning at scale. Amazon's own published account of its CONDOR system is a concrete example of this split: an order isn't solved immediately at checkout — Amazon holds it in a 5-6 hour window before pick-and-pack, re-evaluating the *batch* for that delivery area every ~15 minutes with a mix of mathematical optimization, local search, and vehicle-routing solvers, after a heuristic first narrows millions of raw options down to a handful of viable ones ([Amazon Science, "The science behind grouping Amazon package deliveries"](https://www.amazon.science/latest-news/the-science-behind-grouping-amazon-package-deliveries)). That's periodic batch optimization on a bounded, pre-filtered set — not a per-order ILP solve — the same shape this design follows: a rule-based pipeline as the real router. **This repo implements two comparison baselines against the pipeline:** the naive arm (raw arrival order, same claim logic) and a Hybrid ILP arm (`routing/optimization_ilp.py`, Section 3) that solves the contested subset as one joint mixed-integer program via `pulp`, exactly the "offline benchmark against the live heuristic" role described above — it is not wired into live routing. Full-batch ILP (every order, not just the contested subset, in one joint solve) remains a documented future benchmark (Section 9), not built.

## 3. Final approach: one filter pipeline

The engine is a single pipeline, run in stages: two fact-check filters, a contention scan that splits the batch, one comparison step for the contested remainder, and a sequential claim.

**Stage 1 — Order-eligibility filter:** is it decision time for this order yet? An order becomes eligible the instant its time-to-promise runs out relative to now (or this is its binding cutoff tick). This is a fact about the order in isolation — not a comparison to other orders. Orders that fail this filter aren't in play this round; they stay queued. (Full mechanics in Section 4.)

**Stage 2 — FC-option feasibility filter,** applied to every order that passed Stage 1: for each candidate FC, is it in stock? Is its cutoff still open? Can it hit the promised EDD given its transit time and the FC's remaining pick-pack capacity for the day? Anything that fails is excluded. For a multi-item order, this produces one option row per feasible FC (a **Consolidated** strategy — every item from one FC) plus one row per feasible **Split** combination (each item from its own cheapest feasible FC, total cost summed, effective EDD the max across items since the order isn't done until the slowest piece arrives). Consolidated and Split are just more rows in the same option set — no separate mechanism.

**Contention scan — split the batch into uncontested and contested orders.** An order is uncontested if its cheapest on-time option doesn't draw on a resource (an inventory unit, or an FC's remaining daily capacity) that any other order in the batch also needs. Uncontested orders are assigned immediately — there's no decision to sequence, since no other order is waiting on the same unit. Contested orders — the ones whose options overlap on a scarce unit — go on to Stage 3 and 4. This is what keeps the pipeline fast: most of a batch is usually uncontested, and only the shared-resource subset needs sequencing logic at all.

**Stage 3 — Sort the contested orders** by category, then promise date, then regret cost:

1. **Resolve capacity threats first.** If an order's only on-time option is threatened by an FC capacity limit (not a stock-out), check whether shipping one day later still meets the promise. If yes, that option counts as on-time — a capacity slip that doesn't blow the date isn't a threat.
2. **Count on-time options and assign a category** (Consolidated and Split rows both count):
   - **Safe** — two or more on-time options survive. Losing one still leaves an on-time fallback.
   - **At-risk** — exactly one on-time option survives. Losing it means missing the promise.
   - **Hopeless** — zero on-time options survive. The promise is already unreachable regardless of what happens in this pass.
3. **Process in this order: At-risk, then Safe, then Hopeless last.** At-risk orders get first claim on the scarce unit they need, because losing it is the difference between on-time and late. Safe orders go next — they have a fallback either way. Hopeless orders go last: nothing they claim now changes whether they hit the promise, so they shouldn't be allowed to take a unit an At-risk order needed.
4. **Within each category, sort by promise date ascending, then regret cost (cheapest surviving option vs. second-cheapest) descending.** Category is the primary key; date and regret only break ties inside a category (including among Hopeless orders that still compete for late/backorder resources).
5. **Not a one-shot sort — re-sort before every single claim.** Steps 1–4 don't run once for the whole contested group; `routing/pipeline.py`'s claim loop reruns them against the *remaining* contested orders, live against current inventory/capacity, before picking each next order. A category/regret-cost number computed once at the start of the pass goes stale the instant an earlier claim consumes a resource a later order in the same group was counting on — see the "sequencing-quality" fix below.

**Stage 4 — Sequential claim**, in that live-resorted order, re-checking feasibility again right before actually claiming (belt-and-suspenders on top of Stage 3's own re-sort) since an earlier claim in this same pass can change what's still available:
- An on-time option is still available → claim the cheapest one. For a multi-item order this is an atomic claim: the whole strategy (every item, every FC it draws from) is validated and decremented together, or not at all. Log any cheaper-but-late option passed over.
- Nothing on-time is left → claim the option that minimizes **shipping cost + expected late-penalty cost** (Section 8's cost model), not simply the least-late option — a cheaper option that's later can beat a pricier option that's less late if the penalty doesn't justify the price gap. If every option is later than the 7-day lateness bound, the order is flagged **ESCALATE** instead of auto-assigned — past that point this is an operational decision, not a routing one. Nothing is committed to the ledger for that order, but the cheapest rejected option is still priced and kept on the `Assignment` (`escalated_option`, distinct from `chosen_option`) — it's already this late regardless of what ops does next, so `report.md`'s batch summary counts its cost the same as any auto-routed order's, it just shows `ESCALATE` instead of `yes`/`no` in the on-time column.
- Move to the next order with updated inventory and capacity.

**The "sequencing-quality" fix.** An earlier version of Stage 3 sorted the whole contested group exactly once, up front, then walked that fixed order through Stage 4. Stage 4's own live re-check still claimed the *correct* option for each order either way — nothing was ever assigned against stale stock or capacity — but the *order* orders got their turn in was decided from a snapshot that could go stale the moment an earlier pick in the same group consumed a resource a later order was counting on. Concretely: three orders (A, B, C) each with two on-time options, and only two total units of the resource their best options share. A one-shot sort might rank all three "Safe" (2 on-time options each) using the *original* snapshot; by the time C's turn comes, A and B have already claimed both units C's options depended on, and C's "Safe" categorization was never re-checked against that — C gets whatever's left, having never been correctly flagged At-risk or re-sorted ahead of a less-urgent Safe order in time to matter. The fix (`routing/pipeline.py`, TDD'd against a mechanism test that counts `build_options` calls, not just final outcomes) makes the sort itself incremental: recompute options/categories for the *remaining* contested orders and re-sort from scratch before every single claim, mirroring the loop shape Stage 4 already used for its own live re-check. On this repo's fixture batch, the fix corrected two orders' categories (O3 and O5, from At-risk to Safe) without changing the batch's final on-time count or total cost — a labeling correction, not an outcome change, on this particular batch; a batch where the sequencing actually mattered would show up as a cost or on-time delta, not just a relabeled category.

**Why this over the other two contenders:**

- **Over pure Urgency-Sorted:** the category-first, regret-cost-tiebreak sort captures the cross-order savings and promise-protection that date-only sorting leaves on the table — most concretely, it stops a Hopeless order (already going to miss its date no matter what) from taking a unit an At-risk order still needs to hit its date.
- **Over ILP:** the required hard cases — an FC out of stock, two orders competing for the last unit — are exactly the cases where explainability matters most. This pipeline states, in one sentence per order, exactly why it won or lost a unit and what it cost. A true joint optimizer trades that away: `optimization_ilp.py`'s per-order rationale is "chosen jointly with the rest of the contested batch to minimize total penalty-weighted cost" — true, but it doesn't say *why* the solver preferred this order's option over another's the way Stage 3/4's category-then-regret sort does. Comparison arms:
  - **Naive (implemented)** — same Stage 4 claim logic as the pipeline, but raw `arrival_index` order with no contention scan and no Stage 3 sort. This is what `report.md` compares against the pipeline (labeled **Routing with Contention** in prose, **contention** / **naive** in table columns).
  - **Hybrid ILP (implemented)** — `routing/optimization_ilp.py`. The contested subset is solved as one joint mixed-integer program via `pulp`; everything uncontested still goes through the same fast path as the pipeline, unchanged. **Finding on this fixture batch: it ties the pipeline exactly** — same 13/15 orders on time (of 16 fabricated orders, 1 is deferred by Stage 1's eligibility gate and never reaches either arm — Section 4), same 1 escalation, same $189.20 total effective cost (`report.md`'s "delta (ilp − contention)" row is all zeros; that total includes the escalated order's cheapest rejected option, priced but never committed to the ledger — see this section's Stage 4 bullet above). That means Stage 3/4's category-then-regret sort already reaches the joint optimum *for the contested subset* on this particular batch — the "residual value a true joint optimizer could reach" this section originally speculated about turned out to be $0 here. It does **not** mean the two are equivalent in general: getting to that tie required two real fixes (below) and the gap this arm still can't close (next bullet) is untested on this batch precisely because no order here needs it.
  - **Full ILP (not implemented)** — every order (including today's fast-pathed uncontested ones) and every resource in one joint solve. This is the one gap Hybrid ILP structurally can't close: coordinating a swap between an *uncontested* order and a contested one to free up a better unit for the second (Section 8's documented blind spot) — Hybrid ILP never reconsiders an uncontested order once it's fast-pathed, same as the pipeline. Full ILP remains the theoretical ceiling for batch cost and on-time outcomes; this fixture batch doesn't exercise the gap, so nothing here demonstrates whether that ceiling is actually higher than what Hybrid ILP already reaches.

  **Two design bugs surfaced building the Hybrid arm, both about the gap between a live sequential re-check and a single upfront snapshot:**
  1. **Missing backorder fallback.** The contested subset's options are snapshotted once, before any contested order commits — unlike Stage 4, which live-rebuilds one order's options right before claiming it. `all_candidate_legs_for_fc` returns fresh-stock legs *or* backorder legs, never both, because Stage 4's live rebuild only needs whichever one is true at the instant it claims. A one-shot snapshot doesn't get that luxury: if a losing order's fresh-stock option was the only one captured, and a rival order wins that unit in the joint solve, the loser has no fallback in its own option set and gets wrongly escalated. Fixed by `build_backorder_fallback_options` (`routing/strategies.py`), which adds every FC's backorder path explicitly, even for FCs that look fully stocked at snapshot time.
  2. **Missing ship-date alternatives.** Each FC's "next available ship date" (`earliest_ship_date`) is computed once, greedily, against whatever capacity is left *at snapshot time* — before any contested order has committed. The sequential arms recompute this live after each claim, so a later order in the sort naturally discovers "ship tomorrow instead" once today's slot fills. The one-shot ILP snapshot never gets that: every contested order wanting the same FC sees the *same* single date, so once that date's capacity is spoken for, the solver has no "slip a day at the same FC" choice and jumps straight to a pricier FC instead — even though slipping a day would have been on time and cheaper. Fixed by `build_multi_date_options` (Consolidated) and `build_multi_date_split_options` (Split, one merged leg's date shifted at a time) in `routing/strategies.py`, which enumerate a window of ship-date alternatives per FC instead of the single greedy one, letting the solver's own per-(FC, date) resource constraint (not a heuristic pre-filter) decide who gets which date.

  A related, more subtle fix: the ILP's resource-scarcity constraint originally reused `resolve_capacity_threats`/`worst_case_adjust_multi_leg_options` — the *pessimistic pre-filter* that exists specifically to compensate for Stage 3's sequential blindness to the rest of the batch. The ILP's constraints already see the whole contested batch exactly, so applying that same pessimism on top was double-counting caution and silently discarding options the joint solve could safely have used; removed for the ILP path only.
- **Why Stage 1 stays a separate stage instead of folding into Stage 3's sort:** it's cheap to implement as its own step, and keeping eligibility structurally separate from sorting is what lets Section 4's real cutoff-based version replace the service-level proxy later without restructuring Stage 3.

### The end-to-end sequence

1. Order arrives at checkout → a live feasibility check gives a tentative promise date shown to the shopper (not yet a final FC assignment).
2. Stage 1 runs continuously: the instant an order's time-to-promise runs out (or its binding cutoff tick arrives), it becomes eligible and enters a decision point. Orders still far from their promise date stay queued.
3. Every order that becomes eligible at a given decision point — whether that's a single order admitted immediately, or a group of orders swept in together by a shared cutoff — runs through Stage 2, the contention scan, and (for the contested subset) Stages 3–4 together.
4. The inventory and capacity ledger persists, and the next decision point (next cutoff tick, or the next real-time arrival) repeats from Stage 1.

A low-urgency order isn't a separate real-time mechanism — it's just Stage 1 admitting that one order into its own decision point immediately, rather than waiting for a shared cutoff to admit a group.

### What this prototype actually builds

The sequence above describes the full design, including a rolling scheduler that would trigger Stage 1 repeatedly at real per-FC cutoff times across a day, with an inventory ledger persisted between those runs. **This prototype does not build that scheduler**, but it does build a real, single-shot version of the gate itself. It assumes one already-known group of 16 orders has come in — matching this project's intended scale of a batch of sample orders — and runs the pipeline once over that group:

- **Stage 1 (real gate, minimal version):** `routing/stage1_eligibility.py` implements Section 4's `min(next relevant FC cutoff, order's time-to-promise deadline)` rule with the cheapest inputs that avoid the circularity Section 4 describes — a static candidate-FC lookup (zone distance only, no stock check) and each candidate's cutoff **schedule**, plus a coarse days-to-promise check (calendar days, not Stage 2's exact buffer-days number) standing in for the "time-to-promise deadline" side of the rule. An order is eligible the instant either side fires: a candidate FC has already hit its pack cutoff today, or the promise date is within the urgency deadline — a base of 1 day, scaled up by `routing/zone.py`'s zone-distance table for orders whose nearest candidate FC is more than one zone away, so a farther destination isn't forced in with less transit buffer than it actually needs. Orders that clear neither test are genuinely **deferred** — they never reach Stage 2, the contention scan, or any comparison arm this pass; `report.md`'s "Stage 1 — eligibility (wave release)" table shows every order's decision and why. Of this repo's 16 fabricated orders, 15 clear the gate and 1 (far-zone, high-slack) is deferred, by design, to prove the gate actually holds something back rather than passing everything through. Separately, every *routed* order still gets the original display-only **service level** classification (Expedited/Overnight → high urgency; Standard/Ground → low urgency) and **buffer days**/Stage 2 **on-time option count** snapshot — none of those three change Stage 3's sort order, and the eligibility gate does not use them either (it uses the coarser calendar-days check above specifically to avoid needing Stage 2's output before Stage 2 has run).
- **Stage 2, the contention scan, and Stages 3–4 are implemented** as described above: feasibility filtering (including Consolidated/Split option construction), splitting the batch into uncontested and contested orders, category/date/regret sorting of the contested subset, and sequential claiming with live re-checks against a shared inventory-and-capacity pool.
- **Not built:** the recurring trigger that would re-run Stage 1 at each real FC cutoff throughout the day, the persistent ledger between separate runs, wiring the exact buffer-days number (instead of the coarser calendar-days check) into the eligibility gate, and full-batch ILP. Hybrid ILP **is** built (`routing/optimization_ilp.py`, using `pulp`) as a comparison arm in `report.md` — see Section 3's "Why this over the other two contenders."

### Report and how to run (`run.py` → `report.md`)

`python3 run.py` loads the fabricated batch, runs the pipeline, the naive baseline, and the Hybrid ILP arm (each on its own fresh `World`), and writes **`report.md`** (not HTML). Regenerate after code or data changes.

The report contains:

1. **Intro** — what **Routing with Contention**, **Routing naive**, and **Routing with ILP contention** each do, what each arm optimizes, and the effective-cost formula: `shipping + late penalty + late refund`.
2. **Stage 1 — eligibility (wave release)** — every order in the batch, including any deferred one, whether it cleared the real eligibility gate this pass, and why (candidate-FC cutoff already passed, or the urgency deadline forced it in). Deferred orders appear only here — every section below is scoped to the orders this gate admitted.
3. **Batch summary** — orders on time, % orders on time, % order value on time, orders escalated, total effective cost, and cost per order value, for all three arms plus `delta (contention − naive)` and `delta (ilp − contention)` rows.
4. **Per-order cost table** — side-by-side contention, naive, and ILP columns (FC, shipping, penalty, late refund, effective cost, on-time status) plus both delta columns.
5. **Scenario and rationale** — one table for **Routing with Contention** (shared **tag** for orders that compete for the same resource, e.g. O1/O2 and O11/O12 both tagged `inventory`, scenario note, decision, why that FC/service/cost, and an **impact** column describing cross-order sequencing effects) and a second table for **Routing with ILP contention** (same tag/scenario columns, plus the ILP's own decision and rationale — "chosen jointly with the rest of the contested batch to minimize total penalty-weighted cost" for every solver-assigned order).
6. **Processing order** — claim sequence for contention vs naive when resources are scarce; the ILP arm isn't sequenced (its contested subset is solved jointly in one shot), so it's called out separately rather than shown as a third column.
7. **Stage 1 & 2 time to promise** — service level and service-level classification, promise date, buffer days, Stage 2's on-time-option count, and the contested flag, for the routed subset only.

Tests: `python3 -m pytest -q` (78 tests as of this writing).

### Multi-item orders: split doesn't need a customer flag

The pipeline auto-splits an order across FCs whenever Split is the cheapest feasible strategy, or the only way to hit the promise — it doesn't wait for a checkout-time customer choice to authorize that, any more than it waits for one to authorize which single FC gets picked. A merchant-level opt-*out* for split shipments (e.g., to preserve a single-package unboxing experience) is a reasonable real-world control layered on top later; see Section 9.

Split also rescues the stockout hard case (Section 5): an order with no single FC holding every item can still be fully feasible by sourcing items from different FCs, instead of only falling through to a more distant single FC.

**Shortcut taken:** Consolidated-vs-Split is a two-strategy comparison, not a full search over every possible partial split across 3+ FCs (e.g., two items from FC-A and one from FC-B, out of four candidate FCs). Partial splits aren't explored — real future work (Section 9).

## 4. Order-eligibility filter, in detail: batching window and criteria

Stage 1 needs a rule for *when* an order becomes eligible — this can't be a flat arrival-time window (e.g., "every 24 hours" or "every 5 minutes"), because tolerable delay isn't a function of when an order arrived. It's a function of two things that vary per order:

1. **The FC's pack/ship cutoff.** Every FC has a fixed cutoff time per day (e.g., "orders in by 2pm ship same day"). Holding an order until that cutoff costs nothing — it wasn't shipping before then regardless. This is free optimization room, not a delay traded against the promise.
2. **The order's own time-to-promise.** Time-to-promise = promised date minus the latest ship date that still lets the best-case FC/carrier hit it. An order promised in 9 days on a 2-day-transit lane has enormous time-to-promise; an order promised tomorrow has ~zero time-to-promise, and any delay directly threatens the promise.

**Rule:** an order becomes eligible (Stage 1 passes) at `min(next relevant FC cutoff, order's time-to-promise deadline)` — whichever comes first.

- **Low-urgency orders** (e.g., Standard/Ground promises) become eligible at the *next* pack cutoff, grouped with whatever else is also eligible then.
- **High-urgency orders** (e.g., Next-Day/Expedited promises, or anything within one cutoff cycle of its deadline) become eligible immediately on arrival — waiting even one cutoff cycle could blow the promise.

**Simplified proxy for implementation:** in a live, continuously-running system, computing exact time-to-promise per order means running Stage 2 feasibility before that order is even known to be eligible — circular for the gate that's supposed to decide whether Stage 2 should run yet, and wasteful at scale if it runs for every order the instant it arrives, before there's any batching benefit. A cheaper approximation avoids both the circularity and the per-item stock lookup Stage 2 needs: (1) a **candidate-FC list** — which FCs are within shippable geographic range of the destination, a static zone-distance lookup, not a stock check — and each candidate's fixed **cutoff schedule**, both closer to reference data than live state; and (2) a raw **calendar-days-to-promise** number, compared against a deadline built from the same candidate-FC list — a base of 1 day, plus 1 extra day per zone beyond the nearest candidate's adjacent zone (the same `DAYS_PER_EXTRA_ZONE` table Stage 2's pricing uses), so a farther destination gets a proportionally earlier deadline instead of the same flat number as a nearby one. **`routing/stage1_eligibility.py` builds this version of the gate**: an order is eligible the instant either a candidate FC has already hit its cutoff today, or calendar-days-to-promise is inside that scaled urgency deadline. It's blunter than exact time-to-promise — geography, not stock, decides the candidate set, and calendar days aren't business-day-aware transit time — but it's genuinely load-bearing (Section 3, "What this prototype actually builds"), not a proxy that only feeds a display number. The requested-service-level classification described in Section 3 ("high/low urgency" tag) is a separate, purely cosmetic label — this gate doesn't read it at all.

The one-shot batch report is a different situation: since this prototype already runs Stage 2 for every *eligible* order once, there's no extra cost to also computing that order's buffer days (fastest FC/carrier ETA vs. promise date) for display — `report.md` does this (Section 3). That's a display-only number computed after the fact, still not read back into the eligibility gate above — using it there would mean running Stage 2 before eligibility is decided, the same circularity the calendar-days proxy exists to avoid.

**Why the deadline-scaling increment is flat (1 extra day per zone) regardless of the order's own service level:** this is inherited from `routing/zone.py`'s existing rate model, not a new assumption — `zone_adjusted_rate()` already adds the same flat `+1 day per zone` on top of whatever base transit days a service level starts with, so faster service levels stay faster in absolute terms; only the *increment* is service-level-agnostic. Real carrier zone charts vary that increment by tier (and can make a fast tier outright infeasible past some zone, rather than proportionally slower) — modeling that precisely would mean asking Stage 2's carrier-rate table which service level will actually be used at that zone, the same circularity the calendar-days proxy above exists to avoid. Reusing `DAYS_PER_EXTRA_ZONE` keeps Stage 1 consistent with the rest of the model's existing simplification instead of inventing a second, different one.

**Why condition 1 (candidate-FC cutoff already passed) doesn't check the order's own slack before admitting it:** it doesn't need to — Stage 1 only decides *when an order is seen*, not who wins a contested resource. That's Stage 3's job, and Stage 3's sort already protects against exactly this: `_CATEGORY_RANK` (`routing/stage3_sort.py`) claims **At-risk** orders (few on-time options — genuinely constrained) *before* **Safe** ones (many on-time options — what a high-slack order usually looks like). So a low-urgency order admitted early via condition 1 doesn't get first pick of scarce inventory just because it entered the batch sooner; if it ends up contested against a tighter order, Stage 3 still makes the tighter order claim first. Condition 1's actual justification is FC-side batch-picking efficiency (slot in whatever's ready when a wave is closing anyway) — promise-risk protection is condition 2's and Stage 3's job, not condition 1's.

**Why the candidate-FC list deliberately has no stock check, and isn't on the Section 9 roadmap to add one:** adding one would re-couple Stage 1 to Stage 2's live inventory data — exactly the circularity this section exists to avoid, not a missing feature. It also isn't needed for correctness: cutoffs are an FC-level fact, not a SKU-level one, so a candidate FC's cutoff still fires on schedule regardless of whether it happens to be out of that SKU that day — no order can get stuck waiting on a cutoff that a stock-out would have skipped anyway. If a candidate FC turns out to be out of stock, Stage 2 (which does check stock) catches it the ordinary way once the order is admitted — falling through to another FC, Split, or backorder (Section 5) — never as an eligibility problem.

**Why "last 24 hours" specifically doesn't work:** it's arrival-time-based, not deadline-based, so it's wrong in both directions. It can make an order eligible *before* the FC's actual free cutoff, leaving optimization value on the table for no reason. Or it can hold a tight time-to-promise order for a full day when its real deadline required eligibility hours earlier.

### Consequences of real, per-FC cutoffs

Moving from the simplified proxy to true per-order time-to-promise against real FC cutoffs doesn't change the pipeline in Section 3 — it only changes how precisely Stage 1 computes eligibility. Two things worth designing for up front:

1. **State must persist across decision points.** The inventory ledger and each order's status need to carry forward from one decision point to the next (a 2pm cutoff run has to see what a 10am run already claimed) — a persistent-store requirement, not a fresh one-shot run each time.
2. **Stage 2 is always evaluated live, at decision time — never cached from when the order joined the queue.** Cutoffs are per-FC, so an order's feasible set can narrow purely from clock time (FC-B's cutoff passing) with zero competing orders involved. An FC whose cutoff has passed is excluded by Stage 2 exactly the same way an out-of-stock FC is excluded — a live fact check, computed fresh every time Stage 2 actually runs. Stage 3 is not an exception to this: it doesn't sort from a snapshot taken once at the start of the pass either — it re-runs Stage 2 for the *remaining* contested orders and re-sorts from scratch before every single claim (Section 3's "sequencing-quality" fix), so a category is never more than one claim old. Stage 4 then re-validates each option live one more time, right before actually claiming it, so a claim can never go through against a fact (stock, cutoff, capacity) that's already stale by the time it's committed.

## 5. Hard cases handled

- **FC out of stock:** excluded by Stage 2's feasibility filter, the same way any other unavailable option is excluded; the order falls through to the next-best surviving FC. The fallback includes the Split strategy (Section 3) — an order with no single FC holding every item can still be fully feasible by sourcing items from different FCs, not just by falling through to a more distant single FC. If nothing surviving is a real fallback (no other FC, and Split doesn't cover it either), the order defaults to backorder/pre-order (Section 8) rather than being force-assigned to something that can't actually fulfill it.
- **FC daily capacity oversubscribed:** modeled as a second scarce resource alongside inventory. An FC that's already committed its pick-pack capacity for the day pushes a new claim to the next business day, which flows straight into that option's EDD in Stage 2. Stage 3's category step (Section 3) checks capacity threats first: if next-day shipping still meets the promise, the option stays on-time rather than getting misclassified as a threat.
- **Two orders competing for the last unit (or the last unit of capacity):** resolved deterministically by Stage 3's sort order — category first (an At-risk order claims before a Hopeless one regardless of arrival order), then earlier promise date, then regret cost as the final tiebreak. The losing order is re-routed against remaining FCs through the same Stage 2–4 logic. The log states which order won and why, straight from the sort order — no separate mechanism required.

## 6. Other edge cases (documented, not implemented)

Two additional edge cases are worth documenting here too — distinct from Section 5's hard cases, which the engine must actually handle. Neither is built into this prototype, but reasoning through them changes what belongs on the roadmap in Section 9.

**Weather impact:**
- *What breaks:* the engine's transit-time assumption (carrier + FC → a fixed number of days) is static. A storm disrupting a specific lane or regional carrier hub isn't reflected anywhere — the pipeline would confidently claim an FC/carrier option and compute an EDD from a transit-time figure a live weather disruption has already made unreliable.
- *What it would take:* transit time would need to become a live input (a per-lane delay override or reliability multiplier sourced from a weather/carrier-disruption feed) instead of a fixed constant, consumed by Stage 2's EDD calculation. The pipeline's shape doesn't need to change — only the freshness of one input does.
- *Roadmap link:* reinforces the "live carrier rate and transit-time APIs" item already in Section 9 — weather is one concrete reason that data can't stay static.

**Order cancelled while en route:**
- *What breaks:* this prototype only makes a forward decision (assign → claim → ship). Nothing in Stages 1–4 models reversing a claim or freeing inventory once an order has already shipped — a mid-transit cancellation is a different lifecycle event entirely.
- *What it would take:* a compensating-transaction path — release the already-consumed inventory back to the ledger if the shipment can still be intercepted, or, if it can't, write the loss off outside the routing engine's own cost accounting (the order was correctly routed at assignment time; a later cancellation isn't a routing mistake and shouldn't be scored as one).
- *Roadmap link:* this is the clearest evidence that "decisions are final once made" (Section 8) won't hold in a live system — it means the persistent ledger already planned for the scheduler (Section 9) needs to support a reversal/void operation, not just forward claims.

## 7. Output per order

For every processed order the engine states:

- **Assigned Fulfillment Center(s)** — a single FC for a Consolidated order, or a per-item FC breakdown when the order was Split (Section 3)
- **Carrier & Service Level** — a single value for a Consolidated order, or per-item when Split
- **Estimated Delivery Date (EDD)** — the order's effective date; for a Split order, the max across its items' individual EDDs
- **Total Fulfillment Cost** — summed across items for a Split order, with the per-shipment base fee charged once per (FC, service) pair even when multiple items land there
- **Category at decision time** — Safe, At-risk, or Hopeless (Section 3), and whether the option chosen was capacity-threatened or inventory-threatened
- **Trade-offs made** — cheaper option(s) rejected and why, including which strategy (Consolidated vs. Split) was chosen over the other and why; or, when a promise is missed, the lateness incurred, the expected late-penalty cost factored into the decision (shipping cost + penalty minimized directly, Section 3), and whether the severe-lateness refund applies; or, past the 7-day lateness bound, an **ESCALATE** flag instead of an assignment

### Backorder / pre-order fallback

If an order has no feasible on-time or late option at all — every FC is either out of stock or infeasible on cost — the output is a **backorder/pre-order** flag rather than a forced assignment to a non-existent unit. This is expected to be rare given the safety-stock assumption in Section 8: a real stockout that reaches this engine, rather than an inventory-count bug, is the one scenario this fallback exists for.

## 8. Assumptions and shortcuts

- **Inventory numbers already reflect a safety-stock / available-to-sell buffer applied upstream, before this engine ever sees them.** In a real network, a separate inventory/ATS system holds back a per-SKU buffer specifically to absorb sync latency between sales channels, in-flight orders not yet decremented, and demand spikes — this is the standard industry defense against overselling. This engine assumes that buffer already exists and is maintained by someone else; it is **not** built here and isn't on the roadmap in Section 9 either, because it's a different system's job, not a routing decision. The direct consequence: the classic overselling failure mode (two channels both think they have the last unit because of replication lag) is assumed already prevented before an order reaches this pipeline, so no reconciliation or oversell-correction logic needs to exist in Stage 2 or Stage 4.
- **A genuine stockout — a real zero, not a sync bug — still reaches this engine**, and is handled the ordinary way: Stage 2 excludes that FC like any other infeasible option, the order falls through to the next-best FC or a Split strategy (Section 5), and if nothing feasible remains at all, the order defaults to **backorder/pre-order** (Section 7) rather than being force-assigned. Backordering is itself a standard, deliberate feature — not a failure state — for exactly this case.
- Inventory counts and FC capacity limits are fabricated and static for this fixture batch — no real-time reservation/locking system, since only one pass over one known sample batch is being simulated.
- Carrier rates and transit times are flat, assumed values per carrier/service level, adjusted only by a simplified shipping-zone distance between FC and destination (a linear cost/transit surcharge beyond the adjacent zone, not a real carrier zone chart) — no live rate-shopping API.
- Multi-item orders are supported via a two-strategy comparison (fully Consolidated at one FC, or fully Split to each item's independent best FC) — not a full search over every possible partial-split partition across 3+ FCs, which is combinatorially large. Partial splits (e.g., two of three items from one FC, the third from another) aren't explored, only the two extremes.
- Decisions are final once made in a pass — no re-optimization pass after the fact.
- Stages 2–4, the contention scan (Section 3), and Stage 1's eligibility **gate** are implemented for real. `routing/stage1_eligibility.py` genuinely defers an order (1 of this repo's 16 fabricated orders never reaches Stage 2 this pass) when neither a candidate FC's cutoff has passed nor its own promise date is inside the urgency deadline (Section 4). The rolling scheduler that would re-trigger this gate at real per-FC cutoffs throughout the day, and the persistent ledger between separate runs, are **not built** — the prototype assumes one already-known group of orders and runs the gate, and then the rest of the pipeline, once.
- Stage 1's urgency **classification** (high/low) still uses the simplified service-level proxy (Expedited-or-faster = high-urgency, Standard-or-slower = low-urgency) purely for display — it is not read by the eligibility gate above, which uses a calendar-days-to-promise check instead (Section 4). The buffer days number is likewise a report-only, after-the-fact display computed once Stage 2 has already run for the whole batch (Section 4) — also not read by the gate, for the same circularity reason. Neither the classification nor the buffer days number changes Stage 3's sort order or the eligibility gate's decision.
- **FC capacity is modeled as a real, sometimes-insufficient constraint** — an FC can run out of pick-pack capacity for the day the same way it can run out of a SKU, pushing a claim to the next business day (Section 5). Weather and carrier-network disruptions are still assumed away (Section 6 documents what would need to change to relax that).
- The late-penalty function used in Stage 4's infeasible branch is `max($5, 3% of the line item's value)`, capped by a 7-day lateness bound past which the order is flagged ESCALATE instead of auto-assigned (Section 7) — grounded in typical late-delivery compensation practice, not an invented flat number. On top of that, any option `X=7` days late or more (the same escalation threshold) triggers a **late refund** that tops the penalty up to a full refund of shipping cost — our stand-in for what the merchant paid — capped so penalty + refund never exceed it (`late_refund = max(0, shipping_cost − penalty_cost)`). This is deliberately not modeled as a carrier guarantee — the engine only tracks an ETA estimate, never an actual delivery event, so there's no real carrier commitment to invoke; it's our own severe-lateness goodwill policy. Crucially, shipping cost is a sunk expense — it's already been paid to the carrier, late or not — so the refund is *added* on top of it, not subtracted from it: effective cost in `report.md` is `shipping + late penalty + late refund`, which collapses to roughly `2 × shipping cost` once an option crosses the 7-day bound. An earlier version of this model subtracted the refund from shipping cost instead, which made severely-late options look *artificially cheap* (as low as the flat penalty alone) — exactly backwards, since giving the merchant their money back doesn't get our own carrier spend back. `cheapest_option` (`routing/contention.py`) additionally guards against an option past the 7-day bound (which would escalate, not auto-route) ever outranking a still-routable one on cost, regardless of which cost formula is in effect. **The "stand-in for what the merchant paid" is a real simplification, not a modeled field:** the engine has no separate merchant-payment number anywhere — `shipping_cost` is reused for that role because it's the only per-order dollar figure already computed. Real merchant fulfillment fees (pick/pack/storage/shipping bundled) typically exceed the carrier's shipping cost alone, so the refund cap here likely *understates* what a full merchant-payment refund would actually cost.
- **An escalated order's cost is reported even though nothing was committed.** `claim_order` (Stage 4) and the ILP's `_solve_contested` both price the cheapest option before deciding it's too late to auto-route — that price is a real, already-known number (the order is already this late regardless of what human review decides), so it's kept on the `Assignment` (`escalated_option`, separate from `chosen_option`, which stays `None` since nothing touches the ledger) and counted in `report.md`'s totals the same as any auto-routed order's cost. The only visible difference is the on-time column showing `ESCALATE` instead of `yes`/`no`. For the Hybrid ILP arm specifically, this rejected cost is priced *after* all of that solve's winners are committed — the options snapshot fed to the solver predates those commits and would otherwise misleadingly show a resource a winner just took, so the escalated order's display cost uses a live rebuild against the post-solve ledger, mirroring Stage 4's own live re-check.
- Stage 3's sort is purely risk-based (category, then date, then regret) with no customer or channel priority dimension — every order is ranked only on its own delivery risk, unlike commercial ATP allocation engines that reserve supply by customer tier first (Section 9).
- The contention scan (Section 3) identifies contested orders by primary-demand overlap only — it doesn't check whether an *uncontested* order could free up a better resource for a contested one by taking a slightly worse option. This is a known design gap, and Hybrid ILP (Section 3, implemented) shares it structurally: it also fast-paths uncontested orders and never reconsiders them. On this fixture batch, Hybrid ILP's joint solve of the *contested* subset alone still ties the pipeline exactly (Section 3) — this fixture doesn't happen to contain a case where trading off an uncontested order would help, so it doesn't tell us how large the uncontested/contested gap actually is. A future full-batch ILP baseline (Section 9, not implemented) is the only way to quantify that specific gap, since it's the one difference between Hybrid ILP and Full ILP.

## 9. What I'd build next before this went near a real merchant

- Real inventory reservation/locking to handle concurrent order arrival safely at production volume (a different concern from the safety-stock buffer in Section 8, which defends against overselling — this is about two claims racing on the same in-flight unit).
- **Probability-weighted transit time and cost, from a real carrier-performance API.** Replace the static assumed transit time with a call to an ML-owned service that returns `P(on-time | carrier, service level, lane, target date)` — not just a fixed P90 point, since a single percentile can't answer "on-time by *this* date" for an arbitrary promise. Use it as a hybrid: Stage 2's feasibility filter becomes `P(on-time) ≥ threshold` (still a hard floor, still protects the promise as primary), and Stage 4 minimizes **expected cost** among the options that clear the floor. This prices in real delay-fee and refund risk without turning date-protection into just another cost input.
- The prototype's linear surcharge-per-zone-beyond-adjacent is a simplification of how carriers actually price distance; a live rate-shopping API (per the flat-rate assumption in Section 8) would supply the real per-lane zone number and rate directly instead of an assumed one.
- **A cost-side rescue cap on the on-time branch.** Section 10 documents that Stage 2's hard feasibility cutoff can force an arbitrarily expensive on-time option to auto-commit, with no ceiling — cost is a visible trade-off, not a constraint, so nothing currently stops the engine from paying whatever the last surviving on-time option costs. A smaller, more direct mitigation than the probability-floor hybrid above: a `MAX_ACCEPTABLE_EXPEDITE_COST` (a flat dollar amount, or a % of the order's value) that Stage 4 checks before auto-claiming an on-time option. If the cheapest surviving on-time option exceeds it, flag `ESCALATE` for human review instead of auto-committing — the direct mirror of the 7-day lateness bound already in place on the late branch, just applied to cost instead of days. Not built into this prototype because the fabricated scenario's FC/carrier rates don't naturally produce a cost extreme worth capping, but it closes a real, currently-unbounded exposure in the design as written.
- **The rolling scheduler itself:** a live trigger that re-runs Stage 1 at each real FC cutoff throughout the day, plus a persistent inventory ledger carried between those runs — this prototype only runs the pipeline once over one given group of orders (Section 3), it does not implement recurring cutoffs.
- **Upgrade the eligibility gate's deadline check from calendar-days-to-promise to the real buffer-days number.** The gate built (`routing/stage1_eligibility.py`, Section 4) already uses a candidate-FC cutoff schedule for one half of `min(next relevant FC cutoff, order's time-to-promise deadline)`; the other half is a coarse calendar-days approximation, not Stage 2's exact buffer-days number, because computing that exactly still means running Stage 2 before an order is known to be eligible. Closing that gap for real — not just adding a display number, which already exists (Section 3) — needs an *incremental* Stage 2 check (e.g., cache each candidate FC's last-known feasibility and invalidate on stock/capacity change) so it doesn't have to rerun full feasibility from scratch on every order the instant it arrives.
- **Widen the contention scan beyond primary demand** (Section 8's documented gap) — let it also flag an uncontested order whose second-best option would free up a resource a contested order needs, shrinking the blind spot Hybrid ILP (implemented, Section 3) still shares with the pipeline.
- **Implement a full-batch ILP baseline** (`pulp` is already a dependency; Hybrid ILP is implemented and in `report.md`, Section 3) — every order, including today's fast-pathed uncontested ones, in one joint solve. This is the only way to size the uncontested/contested swap gap above, since it's the one structural difference between Hybrid and Full ILP. Given Hybrid ILP already ties the pipeline exactly on this fixture batch, a fabricated batch specifically designed to contain an uncontested/contested swap opportunity would be needed to make Full ILP's benchmark meaningful.
- Network-level lateness monitoring (is the whole network trending behind, not just this order) to catch systemic problems the per-order view can't see.
- **Full partition search for multi-item orders**, beyond the two-strategy comparison built now (Section 3) — evaluating partial splits across 3+ FCs (not just fully-Consolidated vs. fully-Split), for orders where a partial split would be cheaper than either extreme.
- **A merchant-level opt-out flag for split shipments** — some merchants may want to disable splitting entirely regardless of cost savings (e.g., to preserve a single-package unboxing experience). The current design always auto-splits when it's cheaper or the only way to hit the date, with no override.
- **A demand-class / customer-priority allocation layer above the risk-based sort.** Stage 3 ranks orders purely on delivery risk (category, then date, then regret) — it has no concept of which customer or channel placed the order. Commercial ATP engines (SAP Product Allocation, Oracle Allocation Rules, NetSuite Customer Commit Priority) lead with exactly this: reserve a share of scarce supply for strategic accounts or contractual commitments, then apply date/risk logic within a tier. Fits into this design as a layer on top, not a replacement — sort by demand class first, then by the existing category/date/regret key within each class — but it needs a real input (a customer tier or contract) this project's single-merchant scope doesn't supply.

Rollout path, segment criteria, shadow hypotheses, and write-path closeouts: see [`README.md`](README.md) ("Before integrating and going live" and "Success metrics").

## 10. Risks

- **Garbage-in risk.** The engine is only as good as its inputs (inventory counts, transit times, costs, FC capacity). Section 8's safety-stock assumption removes one specific failure mode (overselling from sync lag) from this engine's surface by pushing it onto an upstream system — but that only holds if that upstream system is actually doing its job; if it isn't, this engine has no way to detect that and will confidently route against a number that was never real. Weather and carrier-network disruptions (Section 6) are a second, separate source of stale inputs this prototype doesn't yet see.
- **Unbounded expedite spend still possible in the feasible branch.** Stage 2's feasibility filter is a hard cutoff applied *before* any cost comparison — a cheap, slightly-late option is excluded outright rather than weighed against an expensive on-time one, so the engine can still be forced into an arbitrarily expensive on-time option purely because the cheaper late option was never in the running to begin with. Section 9 lists two mitigations for this surface, neither built yet: the probability-floor + expected-cost hybrid (relaxes Stage 2's hard cutoff itself), and the simpler cost-side rescue cap (`MAX_ACCEPTABLE_EXPEDITE_COST`, mirroring the existing 7-day lateness bound but on dollars instead of days).
- **Explainability erosion as complexity grows.** Every feature layered on after this prototype — splitting, probability-weighted cost, the ILP exception path — has its own black-box risk. Without a standing discipline (every stage must produce a plain-language reason), the pipeline can drift back toward exactly the opacity this project was designed to avoid.
- **External model dependency.** The probability-weighted cost model (Section 9) depends on an ML-owned carrier-performance API. If that model drifts, goes stale, or has an outage, routing decisions are only as good as an upstream system this engine doesn't control — it needs a static fallback table as a degrade path, not a hard dependency.
- **Checkout-promise/routing-decision consistency.** The tentative promise date shown at checkout (Section 3, step 1) and the actual routing decision made later both depend on feasibility calculations — if the checkout-time promise was computed from stale inventory, nothing downstream re-validates that the promise was ever achievable before the engine starts optimizing around it.
- **Scale and latency are untested.** This prototype is validated only against a small fabricated batch. Behavior, latency, and correctness at real order volume (thousands/day, real concurrent claims) are unknown until load-tested.
- **Segment-selection risk.** Piloting on a segment that doesn't actually have multi-FC decision complexity ([`README.md`](README.md) rollout criteria) would produce a false negative — reading as "the engine doesn't help" when the real issue is that the segment gave it nothing to optimize.
